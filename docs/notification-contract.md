# Единый контракт уведомлений сервисов медиасервера

**Статус:** архитектурная договорённость принята 2026-10-21. Документ задаёт общий стандарт для будущих доработок адаптеров, импортёров/экспортёров и заданий обслуживания. Его публикация не означает, что все существующие компоненты уже реализовали отправку уведомлений.

Связанные документы:
- [Установка и обслуживание Apprise API](apprise-api.md)
- [Telegram и маршрутизация уведомлений](apprise-notifications.md)

## 1. Цель и архитектура

Компоненты сохраняют подробности работы и ошибок в собственных журналах, а значимые события дополнительно отправляют через единый HTTP API Apprise. Компоненты не обращаются напрямую к Telegram и не хранят Telegram-токен, chat ID или topic ID.

Путь доставки:

    сервис → Apprise API → тег категории → сохранённое назначение Apprise → Telegram-тема

Это даёт единый формат сообщений, общую обработку ошибок доставки и возможность менять получателей только в Apprise, без переписывания каждого отправителя.

## 2. Логические параметры конфигурации

Конкретный файл и синтаксис конфигурации зависят от проекта. При добавлении поддержки уведомлений параметры должны соответствовать следующей схеме:

    notifications:
      enabled: true
      apprise_url: "http://<MINI-LAN-IP>:8000"
      config_key: "arr-stack"
      service_name: "JacRed v2 adapter"
      timeout_seconds: 5
      tags:
        critical: "critical"
        warning: "warnings"
        run_info: "run-info"
        library: "library"

Это концептуальный пример схемы, а не готовый конфиг для копирования без адаптации. В рабочей конфигурации указывается фактический LAN-адрес MINI-Ubuntu. Параметр library необязателен для компонентов, которые не уведомляют о появлении контента.

| Поле | Назначение |
|---|---|
| notifications.enabled | Выключает отправку уведомлений, не отключая локальный журнал. |
| notifications.apprise_url | Базовый URL Apprise API, без пути /notify/.... |
| notifications.config_key | Ключ сохранённой конфигурации Apprise; сейчас arr-stack. |
| notifications.service_name | Стабильное человекочитаемое имя отправителя, включаемое в заголовок сообщения. |
| notifications.timeout_seconds | Ограничивает ожидание HTTP-вызова, чтобы шлюз не задерживал основную операцию. Начальная рекомендация — 5 секунд; значение уточняется при внедрении в конкретный компонент. |
| notifications.tags.critical | Тег для критических ошибок; сейчас critical. |
| notifications.tags.warning | Тег для предупреждений; сейчас warnings. |
| notifications.tags.run_info | Тег для итогов выполнения; сейчас run-info. |
| notifications.tags.library | Необязательный тег событий о новом контенте; сейчас library. |

Неизвестные или отсутствующие теги не должны приводить к неявной отправке во все назначения.

## 3. Категории событий

Категория определяет тег маршрутизации. Поле type отдельно описывает характер сообщения.

| Категория | Тег | Apprise type | Примеры |
|---|---|---|---|
| Критическая ошибка | critical | failure | Операция не выполнена, важный источник недоступен, нарушена корректность обработки. |
| Предупреждение | warnings | warning | Восстановимая проблема, частичный результат, пропущенные записи, временная ошибка при продолжении работы. |
| Информация о выполнении | run-info | success или info | Итог разового запуска, число обработанных объектов, длительность и результат. |
| Новое в медиатеке | library | success или info | Уведомление о появлении нового контента, если компонент отвечает за такой сценарий. |

Не отправлять каждую строку WARNING/ERROR из журнала в Telegram. Например, повторяющиеся предупреждения по отдельным элементам следует агрегировать в одно сообщение по результатам операции.

## 4. Заголовок и тело сообщения

Заголовок строится по правилу:

    <service_name> — <краткое описание события>

Примеры:
- JacRed v2 adapter — Ошибка синхронизации
- arr2torr — Выполнение завершено
- Sonarr importer — Часть элементов пропущена

В теле указываются краткое описание, полезные счётчики и рекомендация, где искать подробности. Большие traceback, полный журнал, секреты и чувствительные URL остаются вне Telegram. При необходимости можно указать имя systemd-службы или способ просмотра её журнала.

Использовать именно настроенное service_name, а не hostname или путь к бинарному файлу: имя должно быть стабильным и легко узнаваемым.

## 5. HTTP-контракт

Запрос отправляется на адрес:

    <apprise_url>/notify/<config_key>

В текущей конфигурации это:

    http://<MINI-LAN-IP>:8000/notify/arr-stack

Тело — JSON с полями title, body, type и tag. Пример критической ошибки:

    {
      "title": "JacRed v2 adapter — Ошибка синхронизации",
      "body": "Синхронизация не завершена. Подробности сохранены в журнале службы.",
      "type": "failure",
      "tag": "critical"
    }

Пример предупреждения:

    {
      "title": "arr2torr — Часть элементов пропущена",
      "body": "Обработано 35 элементов; 2 пропущено. Подробности — в журнале.",
      "type": "warning",
      "tag": "warnings"
    }

Пример итога выполнения:

    {
      "title": "arr2torr — Выполнение завершено",
      "body": "Обработано: 120; добавлено: 8; пропущено: 0; длительность: 14 с.",
      "type": "success",
      "tag": "run-info"
    }

Для обычных адаптеров, импортёров и экспортёров используется один config_key — arr-stack, если отдельно не задокументирована причина разделить конфигурации. Тег выбирает получателя; type не заменяет тег.

## 6. Поведение при проблемах с доставкой

Уведомления — дополнительный канал наблюдаемости, а не часть основной логики обработки. Ошибка их отправки не должна превращать успешную операцию в неуспешную или аварийно завершать сервис.

Обязательные требования:
1. Всегда сохранять исходное событие в локальном журнале независимо от доступности Apprise.
2. Ограничивать ожидание HTTP-запроса тайм-аутом.
3. При ошибке доставки записывать локальное диагностическое сообщение со статусом или типом ошибки. Не записывать Telegram-токены, секретные URL и другие секреты.
4. Не делать бесконечных повторов. Если повтор реализуется, он должен быть ограниченным и не создавать поток дубликатов.
5. Не отправлять через тот же шлюз уведомление о неудачной отправке уведомления — это создаёт риск рекурсии.
6. Не превращать Telegram в копию журнала: отправлять только значимые события и сводки по операциям.

Если notifications.enabled равно false, HTTP-запросы к Apprise не выполняются, но локальное журналирование продолжает работать.

## 7. Безопасность

- Не хранить в конфигурации отправителя Telegram-токен, chat ID или topic ID. Эти значения управляются сохранённой конфигурацией Apprise.
- В текущей установке Apprise API не требует логина и пароля и доступен в доверенной домашней LAN. Любое устройство с доступом к API потенциально может отправлять сообщения и управлять конфигурациями. Не публиковать TCP/8000 в Интернете.
- Не помещать секреты и локальный каталог конфигурации Apprise в GitHub.
- В публичной документации использовать заполнитель для LAN-адреса; в рабочем конфиге — реальный адрес.

## 8. Порядок внедрения в компоненты

При доработке каждого репозитория:
1. Проверить текущую систему конфигурации и журналирования; добавить эквиваленты согласованных параметров без поломки существующих настроек.
2. Реализовать helper/client для формирования заголовка, сериализации JSON и вызова Apprise с тайм-аутом.
3. Привязать отправку к действительно значимым событиям; подробности оставить в локальном журнале.
4. Выполнить тест для каждого используемого тега и проверить, что секреты не попадают в вывод.
5. Проверить поведение при недоступном Apprise: основная операция должна продолжаться, проблема доставки — попасть только в локальный журнал.
6. Задокументировать конфигурацию и результаты проверки в репозитории соответствующего компонента.

Не добавлять отдельную прямую интеграцию Telegram в компонент и не дублировать в каждом проекте выбор chat ID/topic ID.

## 9. Текущее состояние на 2026-10-21

- Контракт принят для дальнейшей разработки; существующие компоненты ещё предстоит подключать по одному.
- Apprise API развёрнут на MINI-Ubuntu; исходящий доступ к Telegram выполняется через существующий HTTP-прокси.
- В конфигурации arr-stack протестированы маршруты critical, warnings, run-info и library.
- Seerr настроен на тему library (topic ID 10173); пользователь подтвердил получение тестового уведомления.
